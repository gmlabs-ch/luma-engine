# Definition files

Most of a Wintermute Engine game is described in small text files written
by the engine's editors: `default.game`, `*.scene`, `*.sprite`, `*.actor`,
`*.entity`, `*.window`, `*.font`, `*.items`, `*.def`, `startup.settings`.
They all share one syntax, parsed by the engine's `CBParser`. This document
describes that syntax; the meaning of each block and key is documented per
file type (see the [formats index](README.md)).

Sources: the MIT-licensed
[Wintermute Engine 1.x](https://github.com/MnemonicWME/wintermute-engine)
sources (`BParser.cpp` and the `LoadBuffer` methods of the loaders), and
analysis of game files.

Implemented by the `luma-formats` crate (`luma_formats::def`), and shown by
`luma dump <file>`.

## Example

```
; generated by SceneEdit

SCENE {
  NAME="StoreRoom"
  SCRIPT="scenes\storeroom\scr\scene_init.script"
  EDITOR_COLOR_FRAME { 136,136,136,224 }
  LAYER {
    NAME="main"
    MAIN=TRUE
    WIDTH=1859
    HEIGHT=768
    ENTITY {
      NAME="crate"
      X=521
      Y=720
      SPRITE="scenes\storeroom\crate.sprite"
    }
  }
}
```

## Syntax

A file is a sequence of **statements**. Each statement starts with a
**key**, an identifier made of ASCII letters, digits and underscores (it
may start with a digit: `2D_ONLY`), and continues with one of:

| Form | Example | Meaning |
|------|---------|---------|
| `KEY = value` | `WIDTH=1859`, `NAME="main"` | Assignment of a scalar. |
| `KEY { statements }` | `LAYER { ... }` | A nested block. |
| `KEY { a, b, c }` | `HOTSPOT {25, 24}` | A list of scalars (numbers in practice). |
| `KEY { value }` | `ALPHA { 128 }` | A scalar written in braces: the same as `KEY = value`. |
| `KEY` | | A bare key with no value (no loader accepts one). |

A key may be followed by an optional **name** in single quotes before the
value (`KEY 'name' { ... }`). The engine reads it but no editor writes it.

Keys are matched **case-insensitively**. Each loader has its own table of
keys, and compares what is written with each entry in table order, over
the length of the entry (`CBParser::GetObject`): the first entry the text
starts with wins, and the tables list longer keys before their prefixes
(`ALPHA_COLOR` before `ALPHA`).

A key that is **not in the loader's table is a syntax error**
(`Syntax error in <BLOCK> definition`): the block does not load. What
that means for the file depends on the loader, and is said in each
format's document: most fail the object being loaded (a sprite, a window,
the game), some only drop the part that failed (a layer of a scene, an
entity of a layer, a sub-frame of a frame) and go on. The editors' own
keys (`EDITOR_PROPERTY`, `EDITOR_SELECTED`...) are in the tables and are
accepted. `luma_formats::def::keys` implements the rule, and each loader
of `luma-formats` carries the original's table.

A file's **root block must be its first statement**: the loader reads one
statement and fails with `'<KEY>' keyword expected` when it is another
one. What follows the root block is never read, so a stray `}` at the end
of a hand-written file does no harm.

The same key may appear several times in a block (`SCRIPT`, `FRAME`,
`LAYER`, `POINT`); order is significant.

### Whitespace and comments

Whitespace is spaces, tabs, carriage returns and line feeds. Files written
by the editors use CRLF line endings; readers must accept both. Newlines
carry no meaning: `FONT` followed by `{` on the next line is the same as
`FONT {`.

A `;` at the start of a statement (after whitespace) begins a **comment**
that runs to the end of the line. `;` has no meaning anywhere else, so it
can appear inside strings. Braces are counted inside comments too (see
below): a comment must not hold an unbalanced `{` or `}`. The editors write a header comment such as
`; generated by SceneEdit` and sometimes `; $EDITOR_PROJECT_ROOT_DIR$ ..\..\`,
which the engine ignores.

### Scalar values

After `=`, whitespace is skipped and the value is either:

- a **quoted string**: `"` up to the next `"`. There are **no escape
  sequences**: a backslash is a literal backslash (paths use `\` as
  separator), and a `"` cannot appear inside a string. The value
  `"/\"` is the two characters `/\`. A string that is not closed runs
  to the end of its block;
- otherwise an **unquoted run** of characters: `TRUE`, `-12`, `255,0,0`,
  `left`. The run ends at the first space or control character, at the
  first byte from 0x80 up (the engine tests `char <= 0x20` on signed
  characters, so an accented letter ends an unquoted value), and at the
  end of the enclosing block: `FRAME { DELAY=100}` is well formed. The
  character that ended the run is skipped.

The whitespace after `=` is skipped first, line breaks included: a value
cannot be left empty by writing nothing (`NAME=` followed by a new line
takes the next word); write `NAME=""`.

Loaders then interpret the raw text according to the key:

| Type | Accepted text | Notes |
|------|---------------|-------|
| integer | `-?[0-9]+` | Leading `+` accepted. Trailing junk ignored (`atoi`); text that is not a number is 0. |
| float | `-?[0-9]*(\.[0-9]+)?([eE][+-]?[0-9]+)?` | `atof` semantics; text that is not a number is 0. |
| boolean | `TRUE`, `YES`, `ON`, `1` are true | Case-insensitive. See below for what else is true. The editors write `TRUE`/`FALSE`. |
| string | the raw text | Paths are relative to the game root, with `\` separators. A string of the form `/ID/text` is a string-table reference: the engine looks `ID` up in `string.tab` and falls back to `text`. |
| colour, point, rectangle | comma-separated integers | Written either as an unquoted value (`TRANSPARENT = 255,0,0`) or as a list block (`ALPHA_COLOR { 255,255,255,255 }`). |

These are the rules of `CBParser::ScanStr`, which every loader uses
(`luma_formats::def::scan_int`, `scan_ints`, `scan_float`, `scan_bool`):

- An **empty value** (`X=""`) reads nothing: the variable keeps what it
  had, usually the default.
- A **boolean** compares the leading run of letters and digits of the
  value with `yes`, `true`, `on` and `1`, over the length of that run
  only. Any prefix of one of them is therefore true (`T`, `Y`, `O`,
  `TR`), `TRUE,` is true, and so is a value that starts with no letter or
  digit. `yess` and `10` are false.
- In a **list** (`%d,%d,...`), each number must be followed by a comma
  for the next one to be read; where the comma is missing the scan stops
  and the remaining variables keep what they had. A list may be broken
  over several lines.
- **Colours** are kept within 0 to 255 per component (`Rgba::from_ints`).

Two defects of the original are not reproduced here. Its scan does not
skip a carriage return after a number, so that a list broken over lines
of a CR LF file is read up to its first line break; Luma reads the whole
list. Its `DRGBA` keeps the low byte of each colour component (256 is 0,
-1 is 255); Luma clamps.

Strings are 8-bit text in the game's Windows code page; the files of most
games are plain ASCII.

### Blocks and lists

`{` opens a block that ends at the matching `}`. The engine finds the
closing brace by counting braces without regard to quotes or comments, so
a `{` or `}` inside a string or a comment must be balanced
(`GUID="{665ADE9A-...}"` is fine; `TEXT="}"` ends the block there). A
block that is not closed runs to the end of the file.

The loader receives the **text between the braces** and reads it as its
key requires: as nested statements, as a list, or as a scalar. So
`ALPHA { 128 }` is `ALPHA = 128`, and `CAPTION { two words }` is the
caption ` two words ` with its spaces.

When the content of a block starts with a number, it is a **list** of
scalars separated by commas and whitespace: `POINT {521,720}`,
`AREA { 12, 0, 1012, 100 }`, `RESOLUTION { 1024,768 }`. The loader reads it
with the number of elements it expects (`%D` reads integers until a value
is not followed by a comma); extra elements are ignored, missing ones keep
their default.

An empty block `{ }` is an empty block, not a list.

## File types

Each file type is a sequence of top-level statements, usually a single
root block named after the type:

| Extension | Root block(s) | Written by |
|-----------|---------------|------------|
| `.game` | `GAME`, then `AD_GAME` | ProjectMan |
| `.settings` | `SETTINGS` | ProjectMan |
| `.scene` | `SCENE` | SceneEdit |
| `.sprite` | `SPRITE` | SpriteEdit |
| `.entity` | `ENTITY` | SceneEdit or by hand |
| `.actor` | `ACTOR` | by hand |
| `.window` | `WINDOW` | WindowEdit or by hand |
| `.font` | `FONT` (bitmap) or `TTFONT` (TrueType) | by hand |
| `.items` | one `ITEM` block per item | by hand |
| `.def` | `INVENTORY_BOX` or `RESPONSE_BOX` | by hand |
| `.def` | `INVENTORY_BOX`, `RESPONSE_BOX` | by hand |

Not definition files, despite living next to them: `*.script` (compiled
bytecode in packages, source text in projects) and `string.tab` (one
tab-separated `ID<TAB>text` per line).

## `TEMPLATE`

Most blocks accept a `TEMPLATE = "file"` key. The engine then calls the
object's own `LoadFile` on the spot: the named file, whose root block is
of the same kind, is read **into the object where the key stands**. The
keys written before `TEMPLATE` are overridden by the template, the keys
after it override the template, and what a block appends (the controls of
a window, the nodes of a layer, the scripts) comes in file order.

Values a loader puts together at the end of its block (the tint from
`ALPHA_COLOR` and `ALPHA`, the fade of a window) are the template's
unless the outer block names its own, and the object keeps the name of
its own file (`Filename`). The original gets both wrong, which Luma does
not reproduce: it computes the tint and the fade again from the outer
block alone, losing the template's, and answers the template's name as
the object's file.

A template that cannot be loaded is skipped by some loaders and fails the
object in others; each format's document says which. The original has no
bound on templates naming templates (a file naming itself overflows the
stack); Luma stops a chain at 8 files and a whole load at 1024
(`luma_formats::Files`).

## Notes for implementers

- Find the end of a block by counting braces, as the engine does, and
  keep the text between them: the two ways of reading agree on every file
  the editors write, but hand-written files rely on the engine's.
- Keep the raw text of values and convert on access with the rules above,
  so that an unexpected value (`YES` for a boolean, `1.0` for an integer)
  is handled the way the engine handles it.
- Report the line number of a syntax error; the editors never produce one,
  but hand-written files do.
