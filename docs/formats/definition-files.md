# Definition files

Most of a Wintermute Engine game is described in small text files written
by the engine's editors: `default.game`, `*.scene`, `*.sprite`, `*.actor`,
`*.entity`, `*.window`, `*.font`, `*.items`, `*.def`, `startup.settings`.
They all share one syntax, parsed by the engine's `CBParser`. This document
describes that syntax; the meaning of each block and key is documented per
file type (see the [formats index](README.md)).

Sources: the MIT-licensed [WME Lite](https://github.com/MnemonicWME/wmelite)
sources (`BParser.cpp` and the `LoadBuffer` methods of the loaders), and
analysis of game files.

Implemented by the `luma-formats` crate (`luma_formats::def`), and shown by
`luma dump <file>`.

## Example

```
; generated by SceneEdit

SCENE {
  NAME="StoreRoom"
  SCRIPT="scenes\storeroom\scr\scene_init.script"
  EDITOR_COLOR_FRAME { 136,136,136,224 }
  LAYER {
    NAME="main"
    MAIN=TRUE
    WIDTH=1859
    HEIGHT=768
    ENTITY {
      NAME="crate"
      X=521
      Y=720
      SPRITE="scenes\storeroom\crate.sprite"
    }
  }
}
```

## Syntax

A file is a sequence of **statements**. Each statement starts with a
**key**, an identifier made of ASCII letters, digits and underscores, and
continues with one of:

| Form | Example | Meaning |
|------|---------|---------|
| `KEY = value` | `WIDTH=1859`, `NAME="main"` | Assignment of a scalar. |
| `KEY { statements }` | `LAYER { ... }` | A nested block. |
| `KEY { a, b, c }` | `HOTSPOT {25, 24}` | A list of scalars (numbers in practice). |
| `KEY` | | A bare key with no value (rare). |

A key may be followed by an optional **name** in single quotes before the
value (`KEY 'name' { ... }`). The engine reads it but no editor writes it.

Keys are matched **case-insensitively**. The engine compares each key
against its list of known tokens by prefix, longest tokens first; a
well-formed file never relies on that, and a key the loader does not know
is skipped together with its value.

The same key may appear several times in a block (`SCRIPT`, `FRAME`,
`LAYER`, `POINT`); order is significant.

### Whitespace and comments

Whitespace is spaces, tabs, carriage returns and line feeds. Files written
by the editors use CRLF line endings; readers must accept both. Newlines
carry no meaning: `FONT` followed by `{` on the next line is the same as
`FONT {`.

A `;` at the start of a statement (after whitespace) begins a **comment**
that runs to the end of the line. `;` has no meaning anywhere else, so it
can appear inside strings. The editors write a header comment such as
`; generated by SceneEdit` and sometimes `; $EDITOR_PROJECT_ROOT_DIR$ ..\..\`,
which the engine ignores.

### Scalar values

After `=`, whitespace is skipped and the value is either:

- a **quoted string**: `"` up to the next `"`. There are **no escape
  sequences**: a backslash is a literal backslash (paths use `\` as
  separator), and a `"` cannot appear inside a string. The value
  `"/\"` is the two characters `/\`;
- otherwise an **unquoted run** of characters up to the next whitespace
  character: `TRUE`, `-12`, `255,0,0`, `left`.

Loaders then interpret the raw text according to the key:

| Type | Accepted text | Notes |
|------|---------------|-------|
| integer | `-?[0-9]+` | Leading `+` accepted. Trailing junk ignored (`atoi`). |
| float | `-?[0-9]*(\.[0-9]+)?([eE][+-]?[0-9]+)?` | `atof` semantics. |
| boolean | `TRUE`, `YES`, `ON`, `1` are true; anything else is false | Case-insensitive. The editors write `TRUE`/`FALSE`. |
| string | the raw text | Paths are relative to the game root, with `\` separators. A string of the form `/ID/text` is a string-table reference: the engine looks `ID` up in `string.tab` and falls back to `text`. |
| colour, point, rectangle | comma-separated integers | Written either as an unquoted value (`TRANSPARENT = 255,0,0`) or as a list block (`ALPHA_COLOR { 255,255,255,255 }`). |

Strings are 8-bit text in the game's Windows code page; the files of most
games are plain ASCII.

### Blocks and lists

`{` opens a block that ends at the matching `}`. The engine finds the
closing brace by counting braces without regard to quotes, so a `{` or `}`
inside a string must be balanced (`GUID="{665ADE9A-...}"` is fine).

When the content of a block is scalars separated by commas and whitespace,
with no `=` and no nested block, it is a **list**: `POINT {521,720}`,
`AREA { 12, 0, 1012, 100 }`, `RESOLUTION { 1024,768 }`. The loader reads it
with the number of elements it expects (`%D` reads integers until a value
is not followed by a comma); extra elements are ignored, missing ones keep
their default.

An empty block `{ }` is an empty block, not a list.

## File types

Each file type is a sequence of top-level statements, usually a single
root block named after the type:

| Extension | Root block(s) | Written by |
|-----------|---------------|------------|
| `.game` | `GAME`, then `AD_GAME` | ProjectMan |
| `.settings` | `SETTINGS` | ProjectMan |
| `.scene` | `SCENE` | SceneEdit |
| `.sprite` | `SPRITE` | SpriteEdit |
| `.entity` | `ENTITY` | SceneEdit or by hand |
| `.actor` | `ACTOR` | by hand |
| `.window` | `WINDOW` | WindowEdit or by hand |
| `.font` | `FONT` (bitmap) or `TTFONT` (TrueType) | by hand |
| `.items` | one `ITEM` block per item | by hand |
| `.def` | `INVENTORY_BOX`, `RESPONSE_BOX` | by hand |

Not definition files, despite living next to them: `*.script` (compiled
bytecode in packages, source text in projects) and `string.tab` (one
tab-separated `ID<TAB>text` per line).

## Notes for implementers

- Tokenise with the quoting rules above rather than brace counting, which
  is what the engine does: the two agree on every well-formed file and the
  tokeniser gives better errors on broken ones.
- Keep the raw text of scalars and convert on access, so that an
  unexpected value (`YES` for a boolean, `1.0` for an integer) is handled
  the way the engine would handle it.
- Report the line number of a syntax error; the editors never produce one,
  but hand-written files do.
